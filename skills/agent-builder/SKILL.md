# Agent Builder

为任意领域构建 AI agent：客服、研究、运营、创意工作，或专门的业务流程。

## 核心理念

> **模型本来就知道怎样成为 agent。你的工作，是别挡路。**

Agent 不是复杂工程，它只是一个邀请模型行动的简单循环：

```
LOOP:
  模型看到：上下文 + 可用能力
  模型决定：行动还是回复
  如果行动：执行能力，加入结果，继续
  如果回复：返回给用户
```

**就这些。** 魔法不在代码里，而在模型里。你的代码只是提供了发挥空间。

## 三个基本元素

### 1. 能力（它“能做什么”）

Agent 可以执行的原子动作：搜索、读取、创建、发送、查询、修改。

**设计原则**：从 3-5 个能力起步。只有当 agent 因为缺少某项能力而持续失败时，再增加新能力。

### 2. 知识（它“知道什么”）

按需注入的领域专长：策略、流程、最佳实践、schema。

**设计原则**：让知识可用，但不要强制预装。相关时再加载，而不是一开始全部塞进去。

### 3. 上下文（发生过什么）

把各次行动串成连贯行为的对话历史。

**设计原则**：上下文很宝贵。把噪声大的子任务隔离出去，截断冗长输出，保护清晰度。

## Agent 设计思路

开始构建前，先想清楚：

- **目标**：这个 agent 要完成什么？
- **领域**：它在哪个世界里工作？（客服、研究、运营、创意……）
- **能力**：最关键的 3-5 个动作是什么？
- **知识**：它需要访问哪些专长？
- **信任边界**：你愿意把哪些决策交给模型？

**关键点**：信任模型。不要过度工程化。不要预先写死工作流。给它能力，让它自己推理。

## 复杂度递进

先从简单版本开始。只有真实使用暴露出需求时，再增加复杂度：

| 层级 | 添加内容 | 何时添加 |
|------|----------|----------|
| 基础 | 3-5 个能力 | 一开始总是如此 |
| 规划 | 进度跟踪 | 多步骤任务开始失去连贯性时 |
| 子 agent | 隔离的子执行单元 | 探索过程污染主上下文时 |
| Skills | 按需知识加载 | 需要领域专长时 |

**大多数 agent 根本不需要超过第 2 级。**

## 领域示例

**业务**：CRM 查询、邮件、日历、审批
**研究**：数据库搜索、文档分析、引用
**运营**：监控、工单、通知、升级
**创意**：素材生成、编辑、协作、评审

模式是通用的。变化的只有能力集。

## 关键原则

1. **模型就是 agent**：代码只是在跑循环
2. **能力提供行动手段**：决定它“能做什么”
3. **知识提供判断依据**：决定它“知道怎么做什么”
4. **约束帮助聚焦**：限制能换来清晰度
5. **信任释放能力**：让模型自己推理
6. **迭代暴露需求**：先做最小版本，再根据使用演化

## 反模式

| 模式 | 问题 | 解决办法 |
|------|------|----------|
| 过度工程化 | 在需求出现前就引入复杂性 | 从简单开始 |
| 能力过多 | 模型更容易混乱 | 一开始控制在 3-5 个 |
| 工作流僵化 | 无法适应变化 | 让模型决定 |
| 知识前置塞满 | 上下文膨胀 | 按需加载 |
| 过度微管 | 削弱模型智能 | 信任模型 |

## Agent 心态

**从**："我该怎么让系统执行 X？"
**到**："我该怎么让模型有能力执行 X？"

**从**："这个任务的工作流是什么？"
**到**："哪些能力有助于完成这个任务？"

最好的 agent 代码通常朴素得近乎无聊：简单循环、清晰能力、干净上下文。魔法不在代码里。

**给模型能力和知识，信任它把剩下的事情想明白。**
