# Agent Harness 工程的哲学

> **模型本来就知道怎样成为 agent。你的工作，是为它建一个值得行动的世界。**

## 根本事实

把所有框架、库和架构模式都剥掉，最后剩下什么？

一个循环。一个模型。一个行动邀请。

Agent 不是代码。Agent 是模型本身：一个在全人类问题求解、推理与工具使用经验上训练出来的大型神经网络。代码只是给模型提供表达 agency 的机会。

代码是 harness。模型是 agent。两者不能混淆。混淆了，你就会做错东西。

## Agent 到底是什么

Agent 是一个神经网络：Transformer、RNN、或某个学出来的函数。它经过数十亿次基于行动序列数据的梯度更新，学会了感知环境、推理目标，并采取行动实现目标。

人类是 agent：一个由进化塑造的生物神经网络。DeepMind 的 DQN 是 agent：它从原始像素中学会了 Atari。OpenAI Five 是 agent：五个网络通过自我博弈学会了 Dota 2 配合。Claude 是 agent：它从人类知识的广度中学会了推理与行动。

在每一种情况下，agent 都是训练好的模型。不是游戏引擎，不是 Dota 2 客户端，不是终端。是模型。

## Agent 不是什么

提示词水管工学不是 agency。用 if-else、节点图和硬编码路由把 LLM API 调用串起来，并不会造出一个 agent。它只会造出一条脆弱的流水线：一个把 LLM 当文本补全节点塞进去的鲁布·戈德堡机器。

你不可能靠工程技巧“编出” agency。Agency 是学出来的，不是程序写出来的。再多胶水代码，也不会凭空涌现出自治行为。这类系统是 GOFAI 的现代回潮：几十年前已被抛弃的符号规则系统，重新刷上一层 LLM 的漆。

## Harness：我们真正构建的是什么

如果模型是 agent，那么代码是什么？代码是 **harness**：让 agent 能在特定领域里感知和行动的环境。

```
Harness = Tools + Knowledge + Observation + Action Interfaces + Permissions
```

### Tools：Agent 的双手

工具回答的是：**agent 能做什么？**

每个工具都是 agent 在环境中可以执行的原子动作。文件读写、shell 执行、API 调用、浏览器控制、数据库查询。模型需要理解每个工具是干什么的，但不需要你替它编排顺序，它会自己想明白。

**设计原则**：原子化、可组合、描述清晰。先从 3-5 个开始。只有当模型持续因为缺少某个工具而完不成任务时，再添加。

### Knowledge：Agent 的专长

知识回答的是：**agent 知道什么？**

它把通用 agent 变成领域专家。产品文档、架构决策、监管要求、风格指南。应当按需注入（通过 `tool_result`），而不是预先塞进系统提示词。渐进披露能把上下文留给真正重要的信息。

**设计原则**：知识应当可用，但不是强制装载。Agent 应该知道有哪些知识可用，并在需要时自己拉取。

### Context：Agent 的记忆

上下文把一次次独立动作串成连贯行为。说过什么、试过什么、学到了什么、决定了什么，都在这里。

**设计原则**：上下文很宝贵，必须保护。把会制造噪声的子任务隔离出去（s04）；历史变长时做压缩（s06）；把目标持久化到单次对话之外（s07）。

### Permissions：Agent 的边界

权限回答的是：**agent 被允许做什么？**

对文件访问做沙箱隔离。对破坏性操作要求审批。在 agent 与外部系统之间建立信任边界。这里是安全工程和 harness 工程交汇的地方。

**设计原则**：约束不是为了限制，而是为了帮助聚焦。“一次只允许一个任务 in_progress”会逼出顺序化专注；“只读子 agent”能避免误修改。

### Task-Process Data：Agent 的训练信号

Agent 在你的 harness 里执行的每段行动序列，都是训练信号。真实部署里的感知-推理-行动轨迹，就是微调下一代 agent 模型的原材料。你的 harness 不只是在服务 agent，它还可能帮助 agent 进化。

## 通用循环

每个有效 agent，不论在哪个领域，遵循的都是同一种模式：

```
LOOP:
  模型看到：对话历史 + 可用工具
  模型决定：行动还是回复
  如果行动：执行工具，把结果放回上下文，循环继续
  如果回复：返回答案，循环结束
```

这不是简化图示，这就是实际架构。其他一切都只是 harness 工程：围绕这个循环叠加的机制，让 agent 变得更有效。循环属于 agent，机制属于 harness。

## Harness 工程原则

### 信任模型

最重要的原则：**信任模型**。

不要预判每个边界情况。不要搭复杂决策树。不要预先写死工作流。

模型在推理上，比你能写出的规则系统更强。你的条件分支总会在边角情况失败，模型反而更可能把这些情况推过去。

**给模型工具和知识。让它自己想办法使用。**

### 约束会赋能

这听上去矛盾，但约束不是在限制 agent，而是在帮助它聚焦。

一个“同一时刻只允许一个任务进行中”的 todo 列表，会迫使它顺序专注。一个只读子 agent 会防止意外修改。一个上下文压缩阈值，会避免历史把当前任务淹没。

最好的约束，是防止模型迷路，而不是微观操控它的路径。

### 复杂度渐进增加

不要一开始把一切都建完。

```
Level 0: 模型 + 一个工具（bash）                  -- s01
Level 1: 模型 + 工具分发表                       -- s02
Level 2: 模型 + 规划                             -- s03
Level 3: 模型 + 子 agent + skills                -- s04, s05
Level 4: 模型 + 上下文管理 + 持久化              -- s06, s07, s08
Level 5: 模型 + 团队 + 自主性 + 隔离             -- s09-s12
```

从“可能已经够用”的最低层级开始。只有当真实使用暴露出需求时，再往上走。

## 心智转换

构建 harness 需要一个根本性的思维转变：

**从**："我该怎么让系统执行 X？"
**到**："我该怎么让模型有能力执行 X？"

**从**："用户说 Y 时系统应该怎么反应？"
**到**："哪些工具有助于处理 Y？"

**从**："这个任务的工作流是什么？"
**到**："模型需要什么，才能自己推导出工作流？"

**从**："我在构建一个 agent。"
**到**："我在为这个 agent 构建 harness。"

最好的 harness 代码通常很朴素：简单循环、清晰工具定义、干净的上下文管理。魔法不在代码里，而在模型里。

## 载具比喻

模型是驾驶员，harness 是载具。

编程 agent 的载具是 IDE、终端和文件系统。农业 agent 的载具是传感器阵列、灌溉控制和天气数据。酒店 agent 的载具是预订系统、客户沟通渠道和设施 API。

驾驶员负责泛化，载具负责领域特化。作为 harness 工程师，你的职责是为你的领域造出最好的载具：视野足够清楚、控制足够精准、边界足够明确。

造驾驶舱，造仪表盘，造控制杆。飞行员已经训练好了。

## 结语

模型是 agent，代码是 harness。永远分清你到底在构建哪一个。

你不是在写智能。你是在构建智能栖居的世界。这个世界的质量，直接决定了智能能多清楚地感知、多准确地行动、多充分地利用知识。

造出好的 harness。剩下的交给 agent。
